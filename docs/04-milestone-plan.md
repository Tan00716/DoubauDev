# 《烬堡 EMBERHOLD》开发里程碑验收计划

## 文档定位与使用说明

本文档将《烬堡 EMBERHOLD》的开发范围转化为**可测试、可观察的验收标准**，作为开发团队推进、质检团队测试、项目统筹者决策的**对照基准**。

**范围来源**：技术架构文档第 33 节（MVP / Full 1.0 / Post-Launch 范围划分）。本文档**不修改玩法设计、不做技术选型、不写代码**，仅对已定范围进行验收拆解。

**验收标准原则**：每条标准均满足「玩家可见、可观察、可复现」——不出现「体验良好」「手感不错」等不可判定的表述。

**阅读指引**：

- 开发团队按「验收标准」列逐条实现与自测；
- 质检团队按「质检对照表」执行专项测试；
- 项目统筹者关注「范围冲突 / 待裁决项」附录。

## M1 垂直切片

### 范围定义

**目标**：在技术层面验证「白天建堡 + 夜里守城 + 双层牌库 + 半自动操控」四条核心机制的可行性，产出开发团队内部可运行的技术原型。

> **范围来源说明**：M1 垂直切片是任务指定的里程碑层级，技术架构文档第 33 节仅定义了 MVP 与 Full v1.0。M1 可视作 MVP 的技术预研阶段，其范围严格从 MVP 包含项中抽取「机制骨架」子集，不引入 MVP 范围之外的新系统。

#### 包含清单（Must Have）

| 系统 | M1 范围 | 对应设计文档章节 |
|-|-|-|
| 昼夜循环骨架 | 白天 / 夜间 / 过渡三种状态可切换，有最简 HUD 显示当前阶段 | 核心 Gameplay Loop「Short Loop」 |
| 建造系统骨架 | 1 种建筑（城墙）可在白天放置到地图上，占用工令，永久驻留 | 建造系统 |
| 军团系统骨架 | 1 种单位（盾卫班）可在白天放置，夜间按简单规则自动接敌 | 军团系统 |
| 双层牌库骨架 | 军械册层（城墙卡 / 盾卫卡）白天金币打出后常驻；战术手牌层（1 张占位战术卡）夜间可打出产生效果 | 卡牌系统「牌库分层」 |
| 半自动操控骨架 | 玩家可选中盾卫班并下达「移动/驻守」指令，单位响应执行 | 战斗系统与操控定案 |
| 经济系统骨架 | 金币（初始 500，建造消耗）+ 军令 / 工令容量（初始 6/8） | 经济系统 |
| 敌人系统骨架 | 1 种敌人（狼群）从地图边缘生成，沿直线路径向主堡移动并攻击 | 敌人系统 |
| 主堡与胜负 | 主堡有耐久值，敌人到达主堡后扣减耐久，耐久归零 = 失败 | 一局完整结构与阶段基准 |
| 最简 UI | 屏幕显示：当前阶段（昼/夜）、金币数、主堡耐久、工令/军令容量 | UX/UI「HUD」 |

#### 排除清单（Out of Scope）

| 排除项 | 排除理由 |
|-|-|
| 完整的 3 种建筑 / 3 种单位 | M1 仅验证「落阵→常驻→参与战斗」的闭环，1 建筑 + 1 单位已足够 |
| A/B 升级分支 | MVP 中也为数值提升，M1 完全不做 |
| 战意系统 | M1 中战术手牌仅为占位，不接入完整的接敌产战意循环 |
| 波次系统 / 威胁预演 | M1 中敌人持续生成，不区分波次 |
| 结算 / 存档 | M1 为单次运行原型，不跨会话 |
| 昼夜色调切换 / 特效 / 音效 | 纯技术验证，视觉与音频用占位资源 |
| 多人格敌人 AI | 仅 1 种敌人，走直线路径，不验证流场 / 群体寻路 |

### 玩家视角验收标准

> 注：M1 为内部技术原型，以下验收标准以「开发者以玩家身份操作」为前提，部分标准需在开发者自己运行验证时完成。

| 编号 | 验收标准 | 可观察判据 | 对应设计文档章节 |
|-|-|-|-|
| M1-AC-01 | 玩家能在白天阶段打开建造面板，选择城墙卡，在地图可建造区域点击放置 | 放置后地图上出现城墙实体，金币扣除（如 20 金），工令占用 +1 | 建造系统 |
| M1-AC-02 | 玩家能在白天阶段选择盾卫卡，在地图上点击放置 | 放置后出现盾卫班实体（至少 3 个视觉单位组成方阵），军令占用 +1 | 军团系统 |
| M1-AC-03 | 玩家点击「入夜」按钮后，游戏从白天状态切换为夜间状态 | 屏幕显示「夜间」标识；已放置的城墙和盾卫保留在原地；敌人开始从边缘生成 | 核心 Gameplay Loop |
| M1-AC-04 | 夜间敌人（狼群）生成后沿路径向主堡移动，盾卫班在敌人进入射程后自动攻击 | 观察到敌人 HP 下降、盾卫播放攻击动画；敌人到达盾卫后双方 HP 互减 | 敌人系统；军团系统 |
| M1-AC-05 | 玩家可选中盾卫班，下达「移动」指令至新位置，盾卫班在 3 秒内完成移动并重新进入战斗状态 | 盾卫班整体移动到新位置，移动期间保持队形；到达后自动攻击射程内敌人 | 战斗系统与操控定案 |
| M1-AC-06 | 敌人到达主堡后开始扣减主堡耐久，主堡耐久在 UI 上实时显示扣减 | 主堡耐久数字下降；耐久归零时游戏显示「失败」界面 | 一局完整结构 |
| M1-AC-07 | 玩家在夜间拥有一张战术手牌（占位卡），打出后产生可观察效果 | 打出后手牌消失，效果触发（如：全场敌人减速 50% 持续 5 秒） | 卡牌系统「战术手牌」 |
| M1-AC-08 | 帧率在技术验证机上稳定 ≥60fps（同屏 ≤20 友方 + ≤30 敌方） | 使用 Unity Profiler 或内置计数器确认帧率 | 附录技术假设 |

### 质检对照表

| 风险点 | 质检手段 | 通过标准 |
|-|-|-|
| 放置建筑后实体未正确注册到军械册层 | 代码审查：确认落阵后实体进入持久化对象池；运行时检查对象数量 | 放置 N 个建筑后对象池计数 = N |
| 昼夜状态切换时实体状态未正确保持 | 手动测试：入夜前放置 3 城墙 + 2 盾卫，入夜后确认数量和位置不变 | 实体数量与坐标与入夜前完全一致 |
| 班级指令响应延迟或失序 | 手动测试：连续下达 5 次不同位置移动指令，观察响应顺序 | 5 次指令全部按序执行，无遗漏、无错位 |
| 敌人生成后未正确寻路或卡死 | 手动测试：放置城墙阻断直线路径，观察敌人是否停止或穿墙 | 敌人遇到障碍物后停止（M1 不要求绕行），不穿过碰撞体 |
| 帧率低于 60fps | Unity Profiler 抓取 5 分钟运行时数据 | 95% 以上帧时间 < 16.6ms |

## MVP：可玩最小版本

### 范围定义

**目标**：验证核心 Hook（白天建堡、夜里守城、双层牌库）是否成立。不是技术演示，是**完整可玩的「一个领地 + 一位指挥官 + 三个昼夜循环」**。

> **严格对齐**：以下包含 / 排除清单直接引用技术架构文档 33.1 节，未做增删。

#### 包含清单（Must Have）

| 系统 | MVP 范围 | 对应设计文档章节 |
|-|-|-|
| 昼夜循环 | 完整的白天建造 + 夜间守城 + 结算流程（天亮结算 → 白昼建设 → 入夜预演 → 夜间守城 → 夜末清算） | 核心 Gameplay Loop「Short Loop」 |
| 双层牌库 | 军械册（6 张单位/建筑卡：盾卫、弓手、枪卒、城墙、箭塔、兵营）+ 战术手牌（5 张基础战术卡） | 卡牌系统「牌库分层」 |
| 建造系统 | 3 种建筑：城墙、箭塔、兵营 | 建造系统 |
| 军团系统 | 3 种单位：盾卫、弓手、枪卒 | 军团系统 |
| 敌人系统 | 2 种敌人：狼群、盾卫 | 敌人系统 |
| 指挥官 | 1 名：奥恩（基础规则） | 指挥官系统 |
| 经济系统 | 金币 + 战意 + 军令/工令容量 | 经济系统 |
| 1 张领地地图 | 1 张固定地图，3 个昼夜循环 | 一局完整结构与阶段基准 |
| UI/HUD | 昼夜双态 HUD、手牌显示、建造轮盘 | UX/UI |
| 存档 | 昼夜边界存档 | 附录技术假设 |

#### 排除清单（Out of Scope）

| 排除项 | 排除理由（引自技术架构文档 33.1 节） |
|-|-|
| A/B 升级分支 | MVP 中单位/建筑只有基础形态，升级仅数值提升 |
| 领地扩张 / 地图节点选择 | MVP 为单张固定地图 |
| 精英夜 / Boss 战 | MVP 终局为普通波次加强版 |
| 事件系统 | 复杂度超出 MVP 验证需求 |
| 市集 / 商店 | MVP 中卡牌获取固定为每夜奖励 |
| 诅咒系统 | 非核心体验验证所需 |
| 战旗系统 | MVP 中无领地攻克奖励 |
| Meta 解锁（王国厅） | MVP 为单局体验，无局间循环 |
| 3 名额外指挥官 | 仅奥恩 |
| 5 种进阶单位 | 仅盾卫/弓手/枪卒 |
| 6 种进阶建筑/塔 | 仅城墙/箭塔/兵营 |
| 音效/音乐 | 可用临时音效或静默 |
| 手柄支持 | 键鼠即可 |
| 多语言 | 仅中文 |

### 玩家视角验收标准

| 编号 | 验收标准 | 可观察判据 | 对应设计文档章节 |
|-|-|-|-|
| MVP-AC-01 | 玩家首次进入游戏后，在 5 分钟内理解「白天建造、夜间防守」的节奏 | 观察新手引导完成率：玩家在第 1 个白天至少放置 1 个建筑 + 1 个班，并在第 1 个夜间存活至天亮；引导卡死率 = 0% | 玩家体验目标「早期」 |
| MVP-AC-02 | 玩家能在第 1 昼夜完成「建造 → 入夜预演 → 守城 → 夜末清算 → 天亮结算」全流程且无引导卡死 | 全流程完成率 ≥90%（测试样本 ≥10 人）；无玩家报告「不知道该做什么」 | 核心 Gameplay Loop「Short Loop」 |
| MVP-AC-03 | 玩家能在第一局打出「落阵 → 守城 → 手牌调度」的完整 loop | 第 1 夜至少有 1 次战术手牌打出记录；白天至少有 2 次军械册卡落阵记录 | 核心 Hook |
| MVP-AC-04 | 玩家能感受到「我的城堡就是我的卡组」（卡牌打出后变成场上实体） | 玩家访谈中 ≥80% 能用自己的话描述「卡牌变成了城墙/兵」这一关系 | 核心 Hook；卡牌系统 |
| MVP-AC-05 | 玩家能在白天使用建造轮盘（B 键）选择并放置城墙、箭塔、兵营 | 3 种建筑均可成功放置，放置后金币扣除正确、工令占用正确；建造轮盘可展开/收起 | UX/UI「Build UI」；建造系统 |
| MVP-AC-06 | 玩家能在白天放置盾卫、弓手、枪卒三种单位 | 3 种单位均可成功放置，放置后军令占用正确；单位在地图上以不同视觉外观区分 | 军团系统 |
| MVP-AC-07 | 入夜前 10 秒「威胁预演」显示本轮敌人的路线、数量和到达时间 | 预演面板显示：敌人种类图标、进攻路线箭头、到达倒计时；夜间实际敌人与预演一致 | 战斗系统「威胁预演」 |
| MVP-AC-08 | 夜间敌人分波次进攻，盾卫自动接敌，弓手在射程内自动射击，枪卒对冲锋敌人有反伤效果 | 观察到波次间隔（15 秒窗口）；盾卫与敌人接触后双方 HP 下降；弓手在射程内播放射击动画；骑兵类敌人接触枪卒时受到额外伤害 | 敌人系统；军团系统 |
| MVP-AC-09 | 夜间接敌后玩家战意值增长，可消耗战意打出战术手牌 | 战意 HUD 数字在接敌后持续上升；战术卡打出后战意扣除、效果触发 | 经济系统「战意」；卡牌系统「战术手牌」 |
| MVP-AC-10 | 玩家可给班下达「移动 / 撤退 / 驻守 / 集火」四种指令 | 选中班后右键菜单或快捷键可调出 4 种指令；每种指令执行后班的行为有明显变化 | 战斗系统「玩家操作权限表」 |
| MVP-AC-11 | 指挥官奥恩的被动生效：每夜第一张战术牌免费 | 观察战斗日志或 HUD 提示：第 1 张战术卡打出时战意未扣除 | 指挥官系统「奥恩」 |
| MVP-AC-12 | 天亮后进入结算：建筑自动修复、阵亡班显示召回费用、金币收入到账 | 结算面板显示：修复了多少耐久、召回费用列表、本夜金币收支明细；玩家可选择召回或跳过 | 核心 Gameplay Loop「天亮结算」 |
| MVP-AC-13 | 玩家可在结算后进入下一天白天，继续进行建造和布阵 | 结算面板关闭后，游戏回到白天状态，建造轮盘可用，时间流速可控 | 核心 Gameplay Loop |
| MVP-AC-14 | 第 3 夜（终局）敌人数量和种类显著增加，构成足够挑战 | 第 3 夜至少同时出现 2 种敌人、2 路进攻、总敌人数量 ≥第 1 夜的 2 倍 | 一局完整结构与阶段基准 |
| MVP-AC-15 | 玩家在第 3 夜失败或胜利后，游戏显示结果界面并可重新开始 | 胜利条件：主堡耐久 > 0 且第 3 夜结束；失败条件：主堡耐久归零；结果界面有「再来一局」按钮 | 一局完整结构 |
| MVP-AC-16 | 一局 3 昼夜可在 15 分钟内完成 | 10 局测试平均时长 ≤15 分钟；单局最短 ≥8 分钟（确保不是跳过的） | 游戏身份表「预期单局时长」 |
| MVP-AC-17 | 游戏在昼夜边界自动存档，玩家可「保存并退出」后在下次启动时继续 | 存档后退出游戏，重新启动后可选「继续游戏」；恢复后的状态（天数、资源、实体位置）与退出时一致 | 附录技术假设「存档粒度」 |
| MVP-AC-18 | 无阻塞性 Bug（崩溃、卡死、无法操作的软锁） | 10 局完整测试无崩溃；无玩家报告必须重启才能恢复的问题 | — |
| MVP-AC-19 | 帧率 ≥60fps（目标平台：核显笔记本 @1080p） | 使用最低配置测试机运行，Profiler 显示 95% 帧时间 < 16.6ms | 附录技术假设 |

### 质检对照表

| 风险点 | 质检手段 | 通过标准 |
|-|-|-|
| 数值平衡：第 1 夜过难导致流失 | 10 名非游戏行业测试者首局通过率 | 首局通过第 1 夜的比例 ≥70% |
| 数值平衡：第 3 夜过易缺乏成就感 | 10 名测试者主观难度评分（1–5） | 第 3 夜难度评分 ≥3.5 |
| 新手引导卡死 | 可用性测试：观察新玩家前 5 分钟操作路径 | 无玩家在引导流程中停滞 >2 分钟 |
| UI 可读性：昼夜 HUD 信息过载 | 眼动追踪或主观认知负荷评分 | 玩家能在一瞥（<2 秒）内说出当前金币、战意、主堡耐久 3 个数字 |
| 性能：同屏实体超标导致掉帧 | Profiler + 手动压力测试（第 3 夜最大波次） | 峰值友方 ≤30（3 班 × 最多 8 兵）+ 峰值敌方 ≤60，帧率仍 ≥60fps |
| 存档一致性：恢复后实体位置/血量偏差 | 自动化测试：每夜结束后保存→加载→比对状态哈希 | 10 轮保存/加载循环，状态完全一致 |
| 战意经济：玩家攒战意不花导致后期碾压 | 数据埋点：记录每夜战意结余率 | 平均战意结余率 ≤30%（说明战意有消耗出口） |
| 建造限制：工令/军令容量未正确约束 | 自动化测试：尝试超额建造/招募 | 超出容量后操作被拒绝，并给出明确提示 |

## Full v1.0 / Early Access：完整 Steam 产品

### 范围定义

**目标**：在 MVP 基础上扩展至核心设计文档定义的全部内容，达到 Steam 可上架质量。

> **严格对齐**：以下包含 / 排除清单直接引用技术架构文档 33.2 节，未做增删。

#### 包含清单（Must Have）

| 系统 | Full v1.0 范围 | 对应设计文档章节 |

## 附录 A：范围冲突与待裁决项

### A.1 M1 垂直切片的范围来源

**问题**：技术架构文档第 33 节仅定义了 MVP 与 Full v1.0 两层，未单独定义「M1 垂直切片」。

**处理**：本文档按任务要求将 M1 列为独立里程碑，其范围从 MVP 包含项中抽取「机制骨架」子集，**不引入 MVP 范围之外的新系统**。若项目统筹者认为 M1 应直接合并进 MVP（即跳过独立 M1 阶段），可取消 M1 里程碑，将 M1 验收标准作为 MVP 的内部开发检查项。

### A.2 技术架构文档 33.2 节与核心设计文档的内容量级差异

**问题**：技术架构文档 33.2 节「Full v1.0 新增」清单中，卡牌数量为「初始 60 张」，而核心设计文档写明「初始卡池 60 张（普通 24 / 稀有 20 / 史诗 12 / 传说 4）」。两者一致，无冲突。

**问题**：技术架构文档 33.2 节未明确「8 张领地地图模板」是否全部在 v1.0 中可用，还是部分留作 Post-Launch。

**处理**：本文档按「8 张全部在 v1.0」理解。若需拆分（如 v1.0 仅 4 张，另 4 张 Post-Launch），请统筹者裁决。

### A.3 设计审计报告的 12 条建议级修复

**问题**：设计审计报告中的 12 条建议级发现（如 Normal 难度囤金惩罚、连续失败保护、烬王规则预览、Meta 加权池算法等）已部分纳入本文档验收标准（V1-AC-31、V1-AC-32 等），但其余建议未强制纳入。

**处理**：已纳入的建议在验收标准中标注「设计审计修复」；未纳入的 7 条建议（遗令×战旗协同、敌人图鉴解锁速度、地图模板示意图、手柄操控映射、终局阶段存档、成就系统框架、音效预算量化）作为 **P2 优化项**，不阻塞 v1.0 验收，但建议在开发资源充裕时处理。

### A.4 上架前检查清单中的「用户本人操作步骤」确认

**问题**：Steamworks 开发者账号注册和 \$100 费用缴纳必须由用户本人完成，但用户可能尚未启动此流程。

**处理**：建议用户在 Full v1.0 开发中期（预计开发周期 6–8 个月时）提前完成步骤 A（注册）和 B（缴费），避免开发完成后因账号或支付问题阻塞上架。
